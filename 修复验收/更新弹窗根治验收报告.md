# 更新弹窗（Security validation failure）根治验收

日期：2026-09-18（第三版结论，版本定档 v3.10.4）
涉及版本：v3.10.2 → v3.10.3（方案被证伪）→ **v3.10.4（根治）**

---

## 一、问题

用户操作「下载新版本 → 旧版自动退出 → 新版自动重启」时弹窗：

```
Security validation failure: parent process has different executable!
```

特点：**文件其实已替换完成**（手动再打开就是新版本），但自动重启那一下失败。
v3.10.3 发布后仍复现（文案从 `failed to obtain executable path for parent proces!`
变成了 `different executable`）。

## 二、根因（前一版结论作废，以下为实证结论）

文案来自 **PyInstaller 6.22.2 引导器**，源码依据两块：

`pyi_main.c:205-220` —— 进程是否继承上一次的运行时环境，取决于启动它的
那个人有没有给它留 `_PYI_*` 环境变量：

```c
env_var_value = pyi_getenv("_PYI_ARCHIVE_FILE");
if (env_var_value) {
    if (strcmp(pyi_ctx->archive_filename, env_var_value) == 0) {
        PYI_DEBUG("LOADER: using same archive file as parent environment!\n");
        reset_environment = false;      // ← 认为自己是"继承者"
    }
}
```

`pyi_main.c:496-520` + `pyi_security.c:104-131` —— 一旦走了"继承者"分支，
它就要校验**自己的直接父进程**是不是也跑这个 exe：

```c
if (strcmp(parent_executable, pyi_ctx->executable_filename) != 0) {
    PYI_ERROR_W(L"Security validation failure: parent process has different executable!\n");
    return -1;
}
```

自更新链路正好踩满这两个条件：

```
旧 UnifiedToolbox.exe（本身是 onefile 子进程，带着 _PYI_* 变量）
        │  Popen 派生
        ▼
cmd.exe /c utb_apply_update_xxx.cmd      ← 继承了旧实例的 _PYI_ARCHIVE_FILE 等 3 个变量
        │  start "" "%~2"
        ▼
新 UnifiedToolbox.exe                    ← 又继承了 cmd 的那份脏环境
        → 以为自己是"继承者" → 去校验父进程 cmd.exe
        → strcmp("C:\Windows\System32\cmd.exe", "<自己的 exe>") != 0 → 弹窗
```

**关键点：这条校验不是"路径错了"，是"认错了爹"。**

顺带明确两条此前误导排查的线索：

- 弹窗文本在引导器里是 **UTF-16LE** 存储的，ASCII 扫描永远扫不到。
- 比对双方都用同一个 `QueryFullProcessImageNameW`，同一 exe 理论上必然相等，
  所以"父进程已退出/PID 被复用"的解释在这里解释不通。

### 为什么上一版（v3.10.3，改用 explorer.exe 拉起）没彻底解决

两条原因叠加：

1. **用户那次是用旧版本 exe 升级的** —— 跑的是旧 exe 内置的**旧替换脚本**
   （直接 `start`，没有新逻辑），所以新代码一行都没执行到。
2. explorer.exe 路线只是**碰巧绕开**：explorer 是常驻进程，它拉起的子进程继承的是
   **explorer 自己的干净环境**，脏变量传不过去。它不是正面修复，
   还额外引入了 DDE 兜底、30 秒 cmd 存活、工作目录被改成 System32 等复杂度。

## 三、修复（v3.10.4）

### A. 正面掐断：官方逃生口 `PYINSTALLER_RESET_ENVIRONMENT=1`

`pyi_main.c:178-189` 提供了明确的开关 —— 置 1 就强制作为**全新顶层进程**启动，
直接跳过父进程校验，且引导器**自己会把这个变量清掉**，不会影响它再派生的子进程：

```c
env_var_value = pyi_getenv("PYINSTALLER_RESET_ENVIRONMENT");
if (strcmp(env_var_value, "1") == 0) {
    PYI_DEBUG("LOADER: explicit environment reset enabled via environment variable!\n");
    reset_environment = true;
    pyi_unsetenv("PYINSTALLER_RESET_ENVIRONMENT");
}
```

批处理里必须是 `start ""` 直拉（cmd 用 CreateProcess，环境变量会传下去）；
变量在 `start` 之前 set、`start` 之后清掉：

```bat
set PYINSTALLER_RESET_ENVIRONMENT=1
start "" "%~2"
set PYINSTALLER_RESET_ENVIRONMENT=
```

> 注：这条路对 explorer.exe 无效 —— explorer 拉起时传的是 explorer 自己的环境。

### B. 双保险：派生 cmd 时就把 `_PYI_*` 剔干净

`clean_env_for_update()` 给替换脚本一份过滤后的环境，从源头切断传递。
与 A 各自独立生效，任一命中都不会弹窗。

### C. 保留此前正确的部分

- `--after-update` 仍走临时标记文件 `%TEMP%\utb_after_update.flag`（读到即删）
- 替换脚本文件名唯一化 `utb_apply_update_<pid>_<随机串>.cmd`
  （cmd 边读边执行，固定文件名会被上一轮还活着的脚本覆盖而错位执行）
- `main()` 固定 `os.chdir(exe 所在目录)`（被别人拉起时防相对资源丢失）

### D. 移除的复杂度

explorer 拉起、DDE 丢弃轮询、30 秒 cmd 保险等待全部不再需要，脚本回到 `ping -n 8`。

## 五、验收

### 5.1 控制变量 E2E（关键）

中文路径 `C:\Users\szsz\Desktop\测试\_e2e` 下复刻真实时序
`cmd /c swapper.cmd <新exe> <目标exe> <旧pid>`，**脏环境**变量取自真实运行中的
旧实例（`psutil.Process(pid).environ()` 里读出来的 3 个 `_PYI_*`）。

| 变体 | 环境 | 拉起方式 | 轮数 | PASS | 弹窗 |
|---|---|---|---|---|---|
| A | 干净 | 旧脚本 `start` | 4 | 4 | 0 |
| **B** | **脏** | **旧脚本 `start`** | **2** | **0** | **2/2 💥** |
| C | 脏 | explorer（v3.10.3 方案） | 2 | 2 | 0 |
| D | 脏 | `start` + RESET | 4 | 4 | 0 |
| E | 干净 | `start` + RESET | 4 | 4 | 0 |
| **L** | **脏** | **v3.10.4 产品脚本** | **3** | **3** | **0** |
| **M** | **干净** | **v3.10.4 产品脚本** | **3** | **3** | **0** |

B 组弹出的文案与用户截图**逐字一致**：

```
Security validation failure: parent process has different executable!
```

取证还确认：弹窗时 `UnifiedToolbox.exe` 进程仍在且父进程是 cmd.exe ——
与用户所见（弹窗 + 手动再打开正常）完全吻合。

> 这一步也解释了为什么前一版 E2E 12/12 全过却在真机 100% 复现：
> 旧 E2E 用**干净的外部 Python** 启动 cmd，环境里本来就没有脏变量。
